Recommendation – complete the logon banner

I recommend implementing a standard logon banner across the domain. This supports the FFIEC IT Examination Handbook’s guidance under Information Security – Section II.C.15, Logical Security, which addresses acceptable-use policies and requiring users to acknowledge and agree to those requirements.

Keeping the wording generic lets the same banner serve as a standard configuration across institutions.

Note: one half of the banner is already configured. Windows displays nothing unless both the message title and the message text are set, so the missing half needs to be filled in.

Suggested banner title
AUTHORIZED USE NOTICE
Suggested banner text
This computer system is provided for authorized business use only.

By continuing, you acknowledge and agree to comply with the organization's Information Security, Acceptable Use, and Computer Use Policies.

Use of this system may be monitored, recorded, and reviewed by authorized personnel. Users should have no expectation of privacy when using organization-owned systems, networks, email, internet access, or other technology resources.

Unauthorized access or misuse of this system is prohibited and may result in disciplinary, civil, or criminal action.

By continuing to log on, you acknowledge and consent to these conditions.
Where to set it in Group Policy
  1. Create or edit a GPO linked at the domain root (or the OU covering the workstations in scope).
  2. Browse to Computer Configuration → Policies → Windows Settings → Security Settings → Local Policies → Security Options.
  3. Set Interactive logon: Message title for users attempting to log on to the title above.
  4. Set Interactive logon: Message text for users attempting to log on to the text above.
  5. Both entries are required – setting only one displays no banner at all.
Reference: FFIEC IT Examination Handbook, Information Security booklet, Section II.C.15 “Logical Security”. Have your own legal or compliance function review the wording before deployment – banner language can carry legal weight in your jurisdiction.

What to do with an unrestricted service account

Option 1 – deny it interactive logon

Put the service accounts into a security group and add that group to Deny log on locally and Deny log on through Remote Desktop Services, in a GPO linked where those accounts could otherwise sign in.
Leave Log on as a service and Log on as a batch job in place. Services and scheduled tasks need those rights – removing them stops the application.

Option 2 – convert it to a group Managed Service Account (gMSA)

Active Directory owns the password for a gMSA. It generates a 240-character random password, rotates it automatically every 30 days by default, and hands it only to the hosts you authorise. Nobody ever knows the password, it cannot be typed at a logon prompt, and it never has to be rotated by hand – which also removes the "password never expires" exception that service accounts usually carry.

The domain needs a KDS root key (created once), and the application has to support gMSA. SQL Server, IIS application pools and scheduled tasks do; many third-party applications do not. Where one does not, document the exception and rotate the password on a defined schedule.
