OI-1HighAccount lockout is disabled
The account lockout threshold in Default Domain Policy is set to 0, which disables lockout entirely. An attacker can guess passwords against any account indefinitely without the account ever locking.
ReferenceFFIEC IS II.C.7 User Security Controls
NIST CSF 2.0 PR.AA
CRI Profile PR.AA
CIS Controls v8 6.3; CIS Benchmark - Account Lockout Policy
RecommendationCreate a lockout policy that locks the account after 5 invalid attempts for 60 minutes, with the failed-attempt counter resetting after 15 minutes. During that hour only an administrator can unlock it, so unlock requests go through the help desk and are ticketed. If every lockout must be released by an administrator, set the duration to 0 (locked until unlocked). A threshold of 0 - the current setting - means an attacker can guess passwords indefinitely.

OI-2HighService accounts are not restricted from interactive logon
Three enabled accounts that look like service accounts are not denied "Log on locally" or "Log on through Remote Desktop Services" by any applying Group Policy Object, and no GPO in this domain sets either right, so the Windows defaults apply. One of them is a member of the built-in Administrators group.
ReferenceFFIEC IS II.C.7 User Security Controls (authentication, least privilege)
NIST CSF 2.0 PR.AA
CRI Profile PR.AA
CIS Controls v8 5.1, 5.4
RecommendationRestrict these accounts, or convert them to managed service accounts. To restrict: put the service accounts in a security group and add that group to "Deny log on locally" and "Deny log on through Remote Desktop Services" in a GPO linked where they could otherwise sign in - leaving "Log on as a service" and "Log on as a batch job" in place, because services and scheduled tasks need those and removing them stops the application. To convert: a group Managed Service Account (gMSA) has its password owned by Active Directory, which generates it at 240 random characters and ROTATES IT AUTOMATICALLY every 30 days by default, releasing it only to the hosts you authorise. Nobody ever knows the password, it cannot be typed at a logon prompt, and it never needs manual rotation - which also removes the password-never-expires exception. The domain needs a KDS root key and the application must support gMSA (SQL Server, IIS application pools and scheduled tasks do; many third-party applications do not). Where neither is possible, document the exception and rotate the password on a defined schedule. Create a GPO that denies interactive logon to service and administrative accounts: add the relevant security groups to "Deny log on locally" and "Deny log on through Remote Desktop Services", linked to the workstation and server OUs. Without it the Windows defaults apply and any enabled account can sign in at a console wherever it has access.
